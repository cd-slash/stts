# ESP-32 keyboard (single-device preview)

The PWA has a separate `Keyboard` text field and can also type a coordinator reply. The browser sends text through the authenticated STTS Worker, which calls a loopback bridge through a dedicated Cloudflare Tunnel hostname. A dedicated Cloudflare Access service token protects that hostname; the bridge also checks a separate bearer secret. The bridge supports either a Linux HID gadget's `/dev/hidg0` or a length-prefixed serial link to a keyboard controller. No device secrets reach the browser.

## Hardware and firmware checkpoint

**Live findings (2026-09-26):** `tailscale ssh root@ubuntu-1` works; plain `ssh` is denied by tailnet policy. The device on `ubuntu-1` is USB HID keyboard `Generic USB Keyboard`, serial `STTKBD01`, `1d6b:0102`, high-speed 480 Mbps, Linux gadget version 6.12. The only serial device is a ConBee II ZigBee adapter, unrelated to this keyboard. `STTKBD01` has a keyboard HID interface but no USB serial/network interface; no matching Tailscale node was identified. It is **not an ESP32-S3 USB gadget** (ESP32-S3 USB is full-speed 12 Mbps). The board model and network login are unknown. Its existing Linux OS should be usable for the `/dev/hidg0` bridge if the gadget host has network connectivity and the current keyboard process can be retired. The HID-only USB link cannot be used to reflash, administer, or SSH into that Linux host from `ubuntu-1`. Access to the gadget host (or its physical storage) is needed for deployment. Avoid writing to `/dev/hidg0` alongside another process that may still use it.

The bridge supports US-layout printable ASCII, tab and return. Other layouts and Unicode need explicit mapping before being enabled. A successful response means HID writes completed (or serial firmware acknowledged), not that a foreground application received every character.

## Provisioning when SSH works

1. Identify `STTKBD01`'s physical board, its Linux login/network path and the existing process controlling `/dev/hidg0`. Confirm which machine should receive the keystrokes and retire the prior keyboard process if necessary. No reflashing is needed if this is a reachable Linux gadget with a working HID endpoint.
2. Place `bridge.py` on the **gadget host**, running with `STTS_KEYBOARD_HIDG=/dev/hidg0` and `STTS_KEYBOARD_TOKEN=<independent random secret>`. Use a restricted service user with access to the HID gadget node; its HTTP listener binds to `127.0.0.1:8778` by default. If it turns out to be a separate serial-controlled microcontroller, run the bridge on `ubuntu-1` instead with `STTS_KEYBOARD_PORT=/dev/serial/by-id/<device>` and `pyserial` from `requirements.txt`.
3. Point a Cloudflare Tunnel hostname (for example `keyboard.cdslash.com`) to the bridge at `http://127.0.0.1:8778` on the gadget host (or route the tunnel through a reachable trusted host). Protect this hostname with a dedicated Access application and service-token policy. Create a dedicated token for **this** Access application, not the STTS or Hermes token.
4. Set Worker secrets `KEYBOARD_BASE_URL`, `KEYBOARD_ACCESS_CLIENT_ID`, `KEYBOARD_ACCESS_CLIENT_SECRET` and `KEYBOARD_BRIDGE_TOKEN` (using `wrangler secret put`). The bridge bearer token matches `STTS_KEYBOARD_TOKEN`. Do not put secret values in `wrangler.jsonc`, this repo or client env vars. Test `GET /api/keyboard` from an authenticated session; the UI shows `Connected` only when the bridge receives `PONG` from firmware.
5. With the receiving machine focused on a disposable text field, type a short non-sensitive phrase and verify timing and exact output; test disconnection and reconnect. The UI disables typing while disconnected.

This first version has one configured endpoint; no pairing UI or device IDs are exposed yet. For multi-device support, add an owner-bound device registry with opaque device IDs and per-device keys, a short-lived physical-confirmation pairing flow, revocation, and a per-device queue. Keep device discovery and tunnel credentials on the Worker side.

## Protocol

ASCII bytes only, at most 4096 characters per request. The Worker normalizes CRLF/CR to LF. In HID-gadget mode the bridge writes 8-byte boot-keyboard press and release reports to `/dev/hidg0`; health checks only verify that the node exists, not that the receiving desktop is focused. In serial mode, `PING\n` returns `PONG\n`; `TYPE <count>\n<exactly count bytes>` returns `OK\n` after transmission or `ERR\n` on failure. Commands are serialized at the bridge; an in-flight request returns HTTP 409 to another caller. A timeout can leave delivery ambiguous: do **not** blindly retry a failed typing request; some characters may already have been sent. The bridge never accepts arbitrary keycodes, shortcuts, shell commands or arbitrary device selection.
